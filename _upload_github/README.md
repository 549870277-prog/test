# 东湖听涛 · 游览导览系统

面向到武汉东湖听涛景区游玩的游客：**景点介绍、路口指引、点赞评论、推荐路线可视化与穷举法路线优化**。

前端是零构建的静态站点（原生 ES Module + Three.js），可直接托管到 GitHub Pages，别人打开一个链接就能看；
后端数据库用 **Supabase**（Postgres + PostgREST + RLS），未配置时自动降级为浏览器本地存储，保证站点开箱可用。

- 三维沙盘由你提供的 `blender_model/tingtao.glb` 驱动，路线折线、方向箭头、序号徽章叠加在同一坐标系上
- 路线算法严格按你的规则实现：**Dijkstra 全源最短路 + 穷举法 TSP**，3～5 个景点时毫秒级完成

## 一、快速开始

### 1. 本地预览

```bash
node tools/serve.mjs 5173       # 或 npm run dev
# 打开 http://127.0.0.1:5173/
```

> 必须用 HTTP 服务打开，不能直接双击 `index.html`：ES Module 与 `fetch` 在 `file://` 协议下会被浏览器拦截。
> 推荐用内置的 `tools/serve.mjs`（已显式指定 MIME，Windows 上 Python 的 `http.server` 会把 `.js` 当成 `text/plain` 导致模块加载失败）。

### 2. 跑自检

```bash
npm test                        # 核心算法：51 项断言（连通性、最短路、最优性独立复核、边界、性能）
```

### 3. 发布到 GitHub Pages

```bash
cd "D:/[公众号]/武汉东湖游览程序"
git init && git add -A && git commit -m "feat: 东湖听涛游览导览系统"
git branch -M main
git remote add origin https://github.com/<你的账号>/<仓库名>.git
git push -u origin main
```

然后在仓库 **Settings → Pages** 里把 Source 设为 `Deploy from a branch`，分支选 `main`、目录选 `/ (root)`，保存。
一分钟后访问 `https://<你的账号>.github.io/<仓库名>/` 即可。

> 仓库约 8 MB，其中 `public/tingtao.glb` 占 3.8 MB（GitHub 单文件上限 100 MB，无需 Git LFS）。

## 二、接入 Supabase（后端 + 数据库）

站点默认跑在「本地演示模式」：点赞与评论存在浏览器 localStorage，其余功能完全一致。
要让点赞评论真正落库、多人共享，按下面三步做：

1. 在 [supabase.com](https://supabase.com) 新建项目，进入 **SQL Editor**；
2. 依次执行仓库里两个文件的内容：
   - `supabase/schema.sql` —— 建表（nodes / edges / likes / comments）、索引、触发器、统计视图、RLS 策略
   - `supabase/seed.sql` —— 导入 10 个节点与 12 条道路的种子数据
3. 进入 **Project Settings → API**，把 `Project URL` 与 `anon public` key 填进 `app/config.js`：

```js
export const CONFIG = {
  SUPABASE_URL: 'https://xxxxxxxx.supabase.co',
  SUPABASE_ANON_KEY: 'eyJhbGciOi...',
  // 其余保持默认
};
```

刷新页面，右上角徽标会从「本地演示模式」变成「云端数据 · Supabase」。

### 安全设计

- **anon key 可以公开**：真正的防线是 RLS 策略，不是密钥保密。`service_role` key 绝对不能写进前端。
- 前端在每个请求头注入 `x-visitor-id`，数据库用 `current_setting('request.headers')` 读取它，因此
  「只能删除本人的评论/点赞」是在**数据库层强制**的，不依赖前端自觉。
- 表默认启用 RLS 且默认拒绝，只放行：基础数据匿名可读、本人可写自己的点赞与评论。
- 评论 1–200 字的校验在**数据库 CHECK 约束 + 触发器**里各做一遍；10 秒冷却由 `enforce_comment_rate` 触发器实现。
- 维护人员要人工移除不当内容，用 service_role 连接在 SQL Editor 执行：
  `delete from public.comments where id = '...';`

### 表结构概览

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `nodes` | 入口 / 路口 / 景点，含坐标、简介、建议游览时长 | `type ∈ (entry, junction, poi)` |
| `edges` | 只存**已核实的可步行道路**，距离为道路长度 | `length_m > 0`；不连通就不建行（等价于 ∞） |
| `likes` | 点赞 | `unique(node_id, visitor_id)` —— 同一访客对同一景点只有一个赞 |
| `comments` | 纯文字评论 | `char_length(btrim(content)) between 1 and 200` |
| `node_stats`（视图） | 每个节点的点赞数与评论数 | 一次查询拿全部计数，避免 N+1 |

## 三、路线算法（穷举法）

### 3.1 定位

带固定起终点的旅行商问题（TSP）。首版只覆盖 3～5 个景点，穷举法计算量极小，且能保证**全局最优**，
比动态规划或启发式算法更简单可靠。中间景点数为 n 时需枚举 n! 种排列：

| 中间景点数 | 排列数 | 实测耗时 |
| --- | --- | --- |
| 1 | 1 | 瞬时 |
| 3 | 6 | 瞬时 |
| 4 | 24 | 毫秒级 |

实测 5 景点全流程平均 **0.2 ms**（`npm test` 的性能用例），远低于 PRD 的「3 秒内可用」验收目标。

### 3.2 执行步骤（`app/core/route.js`）

1. **构建节点集**：起点 S、终点 E、目标景点集 T（1 ≤ |T| ≤ 5）；
2. **生成排列**：对中间景点（T 去掉 S 与 E）生成全排列，共 n! 种；
3. **算总距离**：`D = dist(S,P₀) + dist(P₀,P₁) + … + dist(Pₙ₋₁,E)`，任一段为 ∞ 则该排列标记不可达并跳过；
4. **取最优**：可达排列中取距离最小者；距离相同时按中间节点字典序稳定排序；
5. **生成详情**：把最优顺序展开为**完整节点序列（含途经路口）**，逐步给出距离、路口转向提示与序号；
6. **边界处理**：全部不可达 → 列出不可达景点并提示修改；最优距离等于原路线 → 提示「当前顺序已较顺路」；仅 1 个景点 → 直接输出起点→景点。

距离一律取自 `edges.length_m`（已录入道路长度），**绝不用直线距离代替**；不连通的两点记为 ∞。

### 3.3 全源最短路

`buildGraph()` 用 Floyd–Warshall 一次算出 10×10 的最短距离矩阵与**前驱矩阵**，
`graph.path(a, b)` 负责回溯节点序列，`graph.pathGeometry()` 把各段道路折线拼接为完整几何（自动处理折线方向反转）。

### 3.4 步行时间标准

| 游玩强度 | 步行速度 | 依据 |
| --- | --- | --- |
| 轻度散步 | 3 km/h（50 m/min） | 东湖绿道散步节奏 |
| 中度徒步 | 4.5 km/h（75 m/min） | 正常步行速度 |
| 重度骑行 | 12 km/h（200 m/min） | 共享单车绿道骑行 |

输出的「预计纯步行时间」明确标注**不含景点停留**；另外单独给出景点建议停留合计与含停留总时长。
「游玩时间」（全天 / 上午 / 下午）只用于提示路线是否超出该时段合理范围，不参与距离优化。

### 3.5 路口转向提示

对每个途经路口，取「进入路口的最后一段折线」与「离开路口的第一段折线」做向量叉积，
用叉积符号判断左/右转、用夹角判别直行或掉头，再换算成中文方位（如「在『听涛路交汇口』左转，朝西北方向前往『长天楼』」）。
这是基于示意折线推导的，上线前须用实测道路复核。

## 五、数据来源与坐标口径

基础数据有三个互相换算的口径，都在 `app/data/seed.js` 里：

| 口径 | 说明 |
| --- | --- |
| `x_m` / `y_m` | 示意平面坐标（米），原点为片区矩形中心，**X 向东、Y 向北** |
| `lat` / `lng` | 由 `bbox_wgs84`（114.3605–114.3695，30.5640–30.5715）线性映射得到 |
| Three.js 坐标 | `[x/500, 高度, -y/500]`，比例 1:500，glTF 中 Z 轴朝南 |

数据来自 `blender_model/tingtao_network.json`：10 个节点、12 条道路、道路总里程 4450 m，全连通。
**内部景点位置、湖岸形态、道路折线均为示意设计，未参考测绘或实景影像，不能用于实地导航。**

改了基础数据后重新生成：

```bash
npm run seed      # 重新生成 app/data/seed.js、supabase/seed.sql 与封面图
npm run inspect   # 核对 GLB 里的标记名称、变换与包围盒
```

## 七、已知边界与待确认项

1. **基础数据是示意数据**：只有四角坐标来自你提供，内部景点位置与道路折线均为概念设计。
   上线前必须替换为实测岸线、景点坐标、道路中心线与通行属性。
2. **景点简介与封面图为占位内容**：`tools/gen_seed.mjs` 里的 `META` 是示意文案，封面是自动生成的 SVG，
   需按实际情况核实替换为实景照片（放进 `public/covers/` 并改 `cover_img` 路径即可）。
3. **路口转向为几何推导**：基于示意折线，可能与现场实际不一致，需实地复核。
4. **首版未做的功能**：实时拥堵、天气、封路、语音导航、注册登录、购票支付、评论回复与图片评论（均在 PRD 中明确不做）。
5. **身份一致性**：访客标识存在浏览器本地，清空浏览器数据或换设备后会变成新访客（PRD 已声明不保证跨设备一致）。
6. **实时协作未开启**：Supabase 的 Realtime 默认关闭。如需「另一个标签页的评论即时出现」，
   在控制台 Database → Replication 勾选 `comments` 与 `likes` 即可，前端订阅逻辑已预留位置。
7. **面积口径冲突**：`tingtao_network.json` 标注的供给面积 1.2–1.5 km² 与坐标包围盒算出的约 0.72 km² 不一致，
   地图上的比例尺以坐标包围盒（862.6 × 834.9 m）为准。
